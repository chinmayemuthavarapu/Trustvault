## 1. 2026-10-24 · Storage keys silently regenerated by the seed script

- **Asked:** "Write a seed script with one account per role and documents that exercise read, edit, expired and trashed cases. `--reset` should start from a clean data directory."
- **Produced:** `scripts/seed.py` that built `Config()` (which creates development keys inside the data directory) and *then* deleted the data directory for `--reset`.
- **What was wrong:** the files were encrypted with keys that had just been deleted from disk. The next app start generated new keys, and every seeded download failed its integrity check with a 500. Nothing in the seed output said so; it reported success.
- **What I did:** moved the wipe to before configuration is loaded, and smoke-tested a real download of seeded data before committing. The failure mode is also a reason the download route refuses to serve anything that fails GCM authentication rather than returning partial data.
- **Fix:** [`01e6298`](../../commit/01e6298) (caught before the first commit).

## 2. 2026-10-24 · Authorisation: the test suite looked complete and was not (mutation check)

- **Asked:** "Write tests proving one user cannot reach another's documents, one per route, and tests for every rule in `authz.decide()`. The judges will delete an authorisation check and run them."
- **Produced:** ~100 tests, all green, with a stranger test for most routes.
- **What was wrong:** I wrote `scripts/mutation_check.py` to delete each check in turn and re-run the suite. Four deletions **survived**, meaning the tests would have passed with a hole in the code:
  1. removing `authz.require()` from **`revoke_grant`**: nobody tested a stranger revoking someone else's grant; a stranger could have removed people's access to documents they cannot see;
  2. removing the trash rule from `ACCESSIBLE_SQL`: the list endpoint adds its own `deleted_at IS NULL`, which masked the rule, so the SQL rule itself was never tested;
  3. removing the self-protection on admin demotion: masked by the "last admin" rule, because the fixture had only one admin;
  4. removing "delete the browser's previous session on sign-in": the fixation test planted an *invalid* token, so it proved nothing.
- **What I did:** added stranger tests for revoke and dismiss, a test that runs `ACCESSIBLE_SQL` on its own against `decide()` for every user × document, a second admin in the admin-safety fixture, and a real hand-over test (Alice signs in, then Bob on the same browser; Alice's old cookie must die). Re-ran the mutation check until every mutation was caught.
- **Fix:** [`a814f1f`](../../commit/a814f1f), [`bdf4286`](../../commit/bdf4286).

## 3. 2026-10-24 · Session hand-over test assumed login was exempt from CSRF

- **Asked:** "Add a test that signing in as a different user on the same browser ends the previous session."
- **Produced:** a test that signed in as Alice, then posted Bob's credentials to `/api/auth/login` without a CSRF header, and asserted Alice's old cookie no longer worked.
- **What was wrong:** the test failed, and the tempting fix was to exempt `/login` from the CSRF check. That would have been wrong: while a session is live, the login form is a state-changing request like any other, and exempting it allows a cross-site page to swap the victim into the attacker's account (login CSRF). The code was right; the test's assumption was wrong.
- **What I did:** kept CSRF on login, and made the test assert both halves: without the token the second sign-in is refused (403); with it, the previous session is deleted.
- **Fix:** [`a814f1f`](../../commit/a814f1f).

## 4. 2026-10-24 · Audit trail flooded with "suggestions shown" on every page view

- **Asked:** "Owners get access suggestions; record the suggestion and the owner's decision in the audit trail."
- **Produced:** an audit row `suggestion.shown` written every time the document page loaded.
- **What was wrong:** opening one document three times produced three identical audit rows. For an evidence log that's noise that buries real events (the per-document record in the UI was mostly this). It also made the "suggestion" row not correspond to an actual decision point.
- **What I did:** a suggestion is now stored once with an id; the audit row is written only when a suggestion is first made, and carries the `suggestion_id`. When the owner accepts, the grant's audit row embeds the suggestion (id, reason, suggested level) and `confirmed_by_owner: true`, so suggestion and decision are linked in one place.
- **Fix:** [`e567d96`](../../commit/e567d96).

## 5. 2026-10-24 · Upload test used a filename that cannot exist in multipart

- **Asked:** "Test that file names with path traversal, CR/LF header injection and right-to-left override are cleaned."
- **Produced:** an upload test with `"../../etc/pass‮wd\r\nX-Evil: 1.pdf"`.
- **What was wrong:** the test failed with "Unknown field(s): file". A CR/LF inside a multipart filename breaks the multipart encoding itself, so the part arrived as a form field. The test was testing the test client, not my sanitiser, and the "obvious" fix (loosening the unknown-field check) would have weakened mass-assignment protection.
- **What I did:** kept the upload test for traversal and bidi characters, and tested CR/LF stripping on `clean_filename()` directly, plus a check that no injected header appears on the download response.
- **Fix:** [`ab887a4`](../../commit/ab887a4).

## 6. 2026-10-24 · Frontend rendered the word "null"

- **Asked:** "Build the document list with pagination; hide the pager when there is one page."
- **Produced:** `tableHost.replaceChildren(table, pages > 1 ? pager : null)`.
- **What was wrong:** `replaceChildren` turns `null` into the text "null", which showed under every short list (seen in a headless-Chromium screenshot, not in the code review). Harmless, but it is the same class of bug as passing untrusted values to DOM APIs without thinking about what they do.
- **What I did:** a single `put()` helper that drops null/false children, used everywhere instead of `replaceChildren`. All text still goes through `textContent`.
- **Fix:** [`b7426a0`](../../commit/b7426a0).

## 7. 2026-10-24 · Development server trusted forwarded headers it should not

- **Asked:** "Write the gunicorn command for the container."
- **Produced:** `gunicorn ... --forwarded-allow-ips "*"`.
- **What was wrong:** that tells gunicorn to trust `X-Forwarded-*` from any client. The app already uses `ProxyFix` with an explicit hop count (`TV_TRUSTED_PROXIES`); trusting `*` as well would let a client influence the scheme the app thinks it is on, and is exactly the misconfiguration that lets people forge their IP in audit logs (THREATS T61).
- **What I did:** removed the flag; forwarded headers are trusted only through `ProxyFix`, for the configured number of hops.
- **Fix:** [`7f24c7f`](../../commit/7f24c7f).

## 8. 2026-10-24 · Audit view: refused attempts read as if they happened

- **Asked:** "Admin activity log: human-readable event names, with filters by person, event, outcome and date."
- **Produced:** a table that mapped `document.download` → "downloaded" regardless of outcome, with a small red "refused" badge in another column.
- **What was wrong:** found while running an end-to-end browser test (share → download → revoke → retry). Filtering by "Refused" showed rows reading "victor · downloaded · Board minutes October". Anyone skimming the log, or a screenshot of it in an incident report, would read that as Victor having the file. For an evidence log that is the worst kind of wrong: the stored record was correct, but its presentation said the opposite.
- **What I did:** one `eventText()` used by every view: refusals read "tried to download", "tried to open", "failed to sign in"; integrity failures read "download failed integrity check". The per-document record for owners uses the same function.
- **Fix:** [`8f9ab53`](../../commit/8f9ab53).

## 9. 2026-10-24 · A module named `http.py` broke the app on my machine

- **Asked:** "Put the shared request helpers (JSON body allowlist, integer query args) in their own module."
- **Produced:** `app/http.py`.
- **What was wrong:** the tests passed in the AI's environment, but on my Windows machine VS Code's Run button executed `app/http.py` directly. That puts `app/` first on the import path, so this file shadowed Python's standard `http` module, and Flask failed with `ImportError: cannot import name 'abort' from partially initialized module 'flask'`. A module name that collides with the standard library is a trap for anyone running the code differently.
- **What I did:** renamed it to `app/request_helpers.py`, checked no other module shares a standard-library name, and added `.vscode/launch.json` with the three supported entry points (seed, run server, run tests) so nobody runs a package file directly.
- **Fix:** [`007fcd8`](../../commit/007fcd8).
